# Eta 长对话本地改造推荐方案

日期：2026-10-22（Asia/Shanghai）。状态：设计建议，待分阶段实施；本次不修改源码、不编译、不安装、不发送模型请求。

**当前规则：**增长余量、显式启用与本次开发边界以 [v4 定稿](CONTEXT_COMPACTION_V4_IMPLEMENTATION_2026-10-22.md) 为准。v1/v2/v3 均为历史设计；精确观测值不是自动发送边界。独立文本接口中的 Room artifact/CAS 等为扩展架构，不代表本次已经接入；以 v4 交付报告逐项记录的实现与验证状态为准。

## 一、推荐结论

采用一套统一业务流程：**按当前模型预算管理活动上下文，以便携文本摘要替换已覆盖旧历史，原文独立归档可查；支持原生压缩的接口作为可选执行后端。**

保留上游的工具边界与原子替换，保留本地的请求前检查、原文检索、断点和诊断；简化要求模型维护的结构化协议，区分用户软预算、有限本地发送边界和已证实的接口硬限制。重点验收压缩后是否获得可用空间、任务能否继续及信息是否保留，而非只看“压缩成功”。

本方案是基于当前证据的推荐，并非已经证明的全局最优参数。85%/60%、75% 和新增量门槛均为首轮候选值，必须通过 v2 的固定工作负载、信息保留、费用/缓存和不同窗口验收；旧 10%I 门槛已撤回。

## 二、依据与当前边界

### 2.1 三种实现分别提供什么

| 来源 | 采用的部分 | 不直接照搬的部分 |
|---|---|---|
| Codex 官方公开配置 | token 阈值、区分完整上下文与压后新增增长的思路、原生能力显式声明 | 不把某个配置比例当成所有版本的固定算法；不声称已核对桌面私有后端实现 |
| OpenAI Responses 原生压缩 | 返回的新窗口作为下一次输入，而非继续附带已覆盖全文；不透明状态按协议处理 | 第三方 API 不因使用 Responses 路径就视为支持压缩 |
| Eta 上游 v3.3.1 | 最新用户请求保护、完整工具交换边界、先持久化再替换、失败不丢原文 | 仅靠上轮 usage、一次总结整个历史、12,000 字符硬拒绝、仅要求略微变短 |
| 本地改造 | 请求前最终协议预算、容量语义、分段与断点、Journal 检索、取消保护、Trace、线性 IPC | 512 KiB/1 MiB 派生默认作为普遍触发线；模型生成事实 ID/来源/增量操作的复杂协议作为默认必经路径 |

官方依据：[Codex 配置](https://learn.chatgpt.com/docs/config-file/config-reference)、[OpenAI 压缩说明](https://developers.openai.com/api/docs/guides/compaction)。前者公开 token 阈值及 total/body_after_prefix 两种统计范围，后者规定独立压缩返回的窗口应完整用于后续请求。本文其余阈值、状态与迁移方案均为 Eta 设计建议。

上游固定基线为 `v3.3.1 / a7fdfc219ceb52cbbe196beaebdcbb40f3fc81d9`，本次本地源码 HEAD 为 `366ce7dea209e80250a5ff0af75b3d58fcb7470e`。

## 三、上下文组织：原文与活动窗口分开

```text
全部原始对话与工具结果 ──→ Journal（保留已有脱敏规则，可定位检索）
                                  │ 来源区间由客户端绑定
当前模型请求 = 系统/工具定义 + 已提交摘要 + 近期原始轮次 + 当前任务受保护部分
                                  │
                 预检 → 压缩连续旧前缀 → 验证候选 → 原子提交
                                  │
                 下次只发送新活动窗口，不重发已覆盖全文
```

- Journal 的持续增长不等于每次模型输入持续无限增长。不得把全部 Journal 或所有旧区间摘要重新追加到请求里。
- 一次压缩覆盖连续且已验证的消息前缀，保留覆盖终点之后的所有未覆盖原文；禁止用早期摘要配较晚的覆盖游标。
- 最新用户请求、尚未闭合的调用/结果对、协议签名绑定的交换不可切断；近期已完成轮次优先原样保留，但不设一个与模型容量无关的固定轮数。
- 摘要是有损记忆，原始具体数值、日志和工具输出通过 Journal 再查；不承诺摘要逐字保存全部细节，也不把旧失败状态长期冒充当前状态。
- 指令、完整工具定义、摘要与受保护尾部都计入最终请求。必需部分已很大时，不能靠反复总结旧历史解决。

## 四、统一预算策略

### 4.1 token 主导，每次请求前重新评估

设 I 为当前模型可用输入预算，结合已知输入上限、已知总窗口和实际请求的输出预留计算；已有容量语义继续保留。手动配置窗口是客户端配置，不等于供应商已证实的能力。

- 普通候选触发：活动请求输入达到约 `0.85 × I`。
- 压后候选目标：完整最终请求尽量降到 `0.60 × I`，与触发线拉开距离。它是软目标，不是新的触发线；不能为追目标无限合并。
- 最终计量采用当前 Provider 的实际请求构建器，包含工具、指令、图片/协议项。有有效输入 usage（含缓存部分）才校准，不将缓存输入扣掉；缺失/部分 usage 使用 v2 的明确降级模式，不能根据中间 usage_events=0 或仅一个事件计数判定输入数值可用。
- 校准只复用相同模型/端点/协议投影的可比较数据。首轮和切换模型时也做预检，不依赖上一轮 usage 才能触发。
- 容量未知时显示“容量未知”；普通聊天仍受有限本地发送边界 L、已知硬限制 H 和既有协议保护约束，不能无限放大原请求。容量错误可触发原有受限恢复。
- 初版以总活动上下文为准。压后新增量用于效率和失败恢复判断；不直接默认采用 body_after_prefix，以免忽视仍占容量的摘要前缀。
- 手动压缩不要求先达到 85%；对当前可安全覆盖范围执行一次有益整理，沿用候选与提交保护。已低于目标、没有新旧历史可整理时说明无需再次压缩，不从全 Journal 重建并重读整个会话。

### 4.2 字节预算分成三类

| 类型 | 处理 |
|---|---|
| 用户显式的上传软预算 | 保留原值及触发意图；越线可发起有界压缩，失败按原 P0 白名单处理 |
| 有限本地发送边界 L | 接口上限未知时仍限制自动发送体积；越线摘要失败不自动上传原请求，用户可明确授权仅本次尝试越 L |
| 已确认的接口/网关请求体硬限制 | 独立字段记录证据来源和作用范围；尽量压后满足，仍超限则准确报错，不发送明知不被接受的请求 |

**唯一映射：旧 request_byte_budget 原样保留为 B；L 独立解析，不等于 B，也不自动取 max(B,L)。**B<S<=L 仍先触发软压缩，L 仅作额外发送检查。B>L 不抬高 L，界面明确护栏先触发。DeepSeek 本次精确观察边界为 1,782,914 B（约 1.783 MB/1.700 MiB），v3 不向上取整到 2 MiB。其他路由独立迁移；2 MiB 仅在专门验收或用户明确选择后启用，不声称真实 API 上限。

- 显式正数软预算不自动改动；显式 0 仍只关闭软字节触发，不关闭 token 保护、L 或已确认的传输硬限制。设置迁移必须展示这三种量的含义。
- 2 MiB 可以保留为 DeepSeek 用户显式选择，不能变成全局答案。
- 413 只有明确指向请求体且能关联当前路由时才算相应证据；普通 400、502、连接慢或一次超时不能推导具体字节硬限制。
- 对显式软线 B，压后目标沿用首轮候选 `0.75 × B`；触发仍为 `bytes > B`。token 与字节同时触发时同时考虑两种目标。
- 现有 null 的含义会改变，必须使用策略版本迁移与一次说明；不能直接替换 resolver 后静默上线。旧行为保留为可回滚策略，待评估的 1 MiB PR 不按最终方案合并。

### 4.3 “达到目标”与“可以继续”分别判定

1. 覆盖、工具边界、正文完成状态和本地元数据一致，才形成有效候选。
2. 达到压后目标，允许在完整边界提前结束。
3. 正常处理完本轮选定范围后，候选有明显缩减且符合既有容量保护，但余量不足：可提交并明确显示目标未达；不额外发起无界精简。
4. 摘要失败、取消、保存失败、来源不匹配：不使用早期内存候选掩盖错误，不改变原历史和已验证断点。
5. 必需尾部导致目标不可满足：不删工具结果凑空间。能按已知限制继续则说明余量有限；不能继续则指出受保护部分过大，提供新会话或外置原文选项。

## 五、默认摘要：客户端管结构，模型管语义

### 5.1 默认使用便携文本摘要

模型只需总结目标、用户约束、已确认结果、关键标识、未决问题及下一步；允许清晰的自然语言或 Markdown。栏目是提示建议，不是“少一个标题就判失败”的模式。

来源区间、源内容哈希、覆盖游标、策略版本、上下文 revision 和已完成状态均由客户端生成。模型不再负责复制来源 ID、revision、事实 ID，或维护 add/update/remove 协议。

- 不以 16/64 条事实、精确字段集合或固定 12,000 字符作为默认聊天摘要的必经门槛。
- 保留严格的传输完成、非空、没有实际工具调用、协议泄漏防护、候选预算和存储内存上限。合法引用某个错误码或 `<DSML>` 文本不等同于实际协议泄漏。
- 正文超出软输出目标时，先测量完整候选。仍有效且有空间的完整摘要不因字数轻微超限而必败；确实过大时只允许一次针对性精简，不本地裁去末尾。
- 摘要输出 token 预算按模型能力和最终候选余量分配；首轮上限候选为 8,192 tokens，并受实际能力下调。未知或不支持的输出参数不盲发，内存硬上限与输出目标分开。
- 结构完整不代表事实正确。质量通过冻结问题集和原文核对验收，不能靠放松校验自称“解决”。摘要内容始终作为历史数据，不能覆盖更高优先级指令。

现有结构化任务记忆不直接删除：作为可读取的旧格式/可选后端保留，退出新普通会话的默认必经链。旧的 verified facts 可以由客户端无损渲染为已验证输入，再在需要时做有损文本归纳；不能假装二者完全等价或把格式转换冒充模型验证。

### 5.2 优先只压需要处理的旧前缀

- 保留已有摘要，按连续完整边界选择能够恢复目标余量的最小旧历史前缀；候选估算后仍需完整请求复测。
- 选定输入能在摘要模型预算与本轮限额内完成时，一次摘要即可，不强制“先逐叶抽取，再语义合并”。
- 真正超过摘要模型容量、摘要请求自身传输限制或单次处理预算时，才用分段引擎。输入容量失败可缩小片段；输出慢不自动等同于输入过大。
- 长任务中新增的已完成工具交换也可在安全边界归纳，不能只按用户消息数量触发。
- 持续使用“已有有界摘要 + 新旧前缀”滚动更新；只在实际预算需要时合并已有区间，避免每轮把全部旧区间重新归并。
- 不从“总历史 270 段”推导“每次必须处理完 270 段”。达到有效覆盖和候选目标即可停；未覆盖尾部完整保留。

## 六、失败恢复：阻止跨轮次的无收益重复

保留 2002 的同一用户任务内 byte-only 失败抑制；补上跨运行的有条件失败记录，避免用户每发一条补充就重新承担同一个失败摘要。

失败记录使用 Room 的 compaction_failure_state 表，与上下文 generation 及快照事务关联；具体 schema、显式迁移、canonical/HMAC、版本失效、租约和手动单次绕过见 v2 第 5 节。记录只含安全元数据，不保存凭据或模型正文。

- 对同一来源前缀、相同后端与预算策略的 byte-only 已知摘要失败，新用户消息本身不立即清除失败记录。
- 持久性格式/长度失败只在用户明确重试或相关版本/参数改变时重新评估，不因新增量解锁。无收益失败使用 v2 的 `clamp(2%I,4096,16384)` 或有界字节新增量；传输暂时错误另有时间条件。撤回统一 10%I 门槛。
- token 压力、已确认的容量拒绝与显式手动压缩不受软字节延期阻断，继续执行已有安全恢复；同一无效状态不能通过“token 恢复”无限循环。
- 每次压缩的自动结构/传输恢复共享最多一次恢复额度；单次 120 秒、整体十分钟及请求总量上限先保留作上界，不以扩大它们改善表面成功率。正常用户轮次不应主动消耗完整上界。
- 一轮请求前最多完成一次压缩任务，重建并复测后发送或准确退出；不能在同一发送操作中开启新的压缩任务循环。
- 只有已知 byte-only 摘要失败可沿 P0 发送原请求；不能把 token/both 压力、取消、存储或未知错误降级。
- 取消后绝不继续模型请求、不提交未完成候选；断流后保留工具结果和检查点，不重放已完成 Android 工具。

## 七、断点、模型切换与历史修改

将“语义成果”和“执行设置”分开记录，但保留旧格式读取器：

| 对象 | 复用原则 |
|---|---|
| 完成且来源匹配的便携区间摘要 | 可跨模型/供应商重新验证后复用，重新检查质量版本与最终容量 |
| 尚未完成的输出/未验证合并 | 不复用成已完成成果 |
| 分片尺寸、超时、输出参数、目标预算 | 按新摘要模型重新计算 |
| 原生加密压缩项、签名推理项、previous_response_id | 不直接跨供应商、账号、模型或不兼容会话移植 |

- 新断点的源标识基于有序消息内容、区间与摘要语义版本，而非把 API Key、全部 config 等无关变更一并作为语义缓存失效条件。摘要模型与提示版本另存用于判断兼容性，不盲目复用。
- 已存在的旧 270 段、文本断点和分层树继续由旧读取器恢复，不强行转换或删除。迁移失败仍保留原文件，可走旧流程。
- 用户切模型/API 后，发送前立即重算最终协议、输入预算与输出预留；小窗口不足则先压缩，不能沿用旧模型容量。
- 编辑/重新生成使相应来源区间失效，从最早受影响的摘要依赖向后重建；不能重新插入已被当前摘要覆盖的完整原历史。
- 原子提交使用源 revision 检查。压缩期间收到新补充，提交时仅覆盖原先选定范围，新追加消息与工具结果不得丢失；源前缀已改变则拒绝旧候选。

## 八、原生压缩后端

这是可选加速/质量后端，不是整套方案依赖：

1. 按官方文档、供应商显式能力与已验证模型/协议启用，默认不探测真实会话，不因支持 Responses 就自动启用。
2. 原生返回的新窗口按其协议完整承接；不能套用本地“摘要字符串 + 尾部”拼装法裁剪原生返回结果。
3. 切供应商需要便携上下文时，从已有便携摘要与 Journal 在预算内构建，不解释、猜测或伪装迁移加密内容。
4. 暂不为每次原生压缩额外并行生成一份便携摘要，避免双重费用与延迟；未来切换确需生成时再执行并向用户说明。
5. 不支持能力的明确拒绝可退回普通摘要一次；鉴权、账户限额、取消、存储错误不伪装为“原生不支持”。不自动切到另一个供应商。

对当前 DeepSeek、intern-ai、WorkBuddy，推荐普通便携摘要为默认；没有新增能力证据前，不调用原生压缩端点。已有 Anthropic/Responses 原生实验项先维持受保护、可回滚状态，不在本轮追求全面接入。

## 九、用户界面与可观测性

界面只展示有意义的状态：

- “正在整理旧上下文，近期消息将保留。”
- “正在生成摘要，已等待 …；原历史仍保留。”
- “已压缩并释放空间”仅在实际达到目标时显示。
- “已缩减，近期必要内容较大，余量有限。”
- “本次自动压缩未完成，原历史已保留；已暂停重复尝试。”并给出重试入口及真实原因。
- “模型容量未知”与“接口请求体过大”分别提示，不统一称“上下文超限”。

保留分段进度与中间态，但不预报未知总段数。计数只在验证及保存成功后前进；显示已完成与预计目标，不把正常流式生成说成超时。

日志沿用请求 Trace 和 preparation 计时，增加安全数值：压前/压后输入与字节、估算/真实 usage 来源、目标是否达成、延期原因、调用次数、总摘要耗时、压后新增量及再次触发间隔。正文、思考、工具参数/结果、API Key 不进入遥测。

## 十、实施顺序及验收

分为四个可独立回滚的阶段，避免同时更换触发、格式和断点导致无法归因。

| 阶段 | 工作 | 通过条件 |
|---|---|---|
| A：统一预算与候选判定 | token 前检保留；完成两种摘要路径压后目标；自动字节策略先 shadow；显式覆盖不动 | 1.78 MiB 且 token 未受压的样本不因未知传输上限启动摘要；85%/60%、B/T 边界及必要尾部正确 |
| B：默认便携摘要 | 文本摘要适配相同分片/断点/候选引擎；客户端绑定来源，旧结构化路径保留 | 17 条事实不再是文本路径错误；完整响应、容量、来源、工具边界和取消仍受保护；文本与分层终态一致 |
| C：增量与跨运行恢复 | 仅处理连续新增旧前缀；可迁移成果与执行设置分开；失败记录、历史修改依赖校验 | 连续工具及多次用户补充不产生同源失败风暴；换 API 复用已验证成果；旧断点与新补充不丢失 |
| D：原生后端与正式灰度 | 已支持接口能力检查、不可移植状态隔离；批准后真机验收与默认迁移 | 支持/不支持/切模型/取消均正确；用户实际成功继续任务，不仅得到“压缩成功”通知 |

阶段 A 的 null 默认切换需要阶段 B/C 的恢复与质量验证完成后才进入正式灰度；shadow 不发送额外请求。`366ce7d` 可以复用，但不能仅因其测试通过就跳过文本路径与策略迁移验收。

### 必测清单

1. **正常长对话**：同一历史在大窗口不误压缩，换小窗口先预检；缓存 usage 仍占上下文。
2. **真正越线**：触发后候选明显缩减；有限轮次内继续聊天；后续相同负载下再次触发间隔比旧策略改善，不保证任意巨型工具结果都不会再触发。
3. **无收益或失败**：不会每个工具/补充轮重新花费几十秒；token 危险时仍保留硬保护。
4. **摘要质量**：冻结原文中的已知目标、禁止事项、已完成操作、关键数值/路径与未决状态能正确保留；随机具体工具结果可经 Journal 回查。模型文字的语义质量需真实验收，单测不能证明。
5. **格式与传输**：空响应、截断、超长、合法引用 DSML、实际泄漏、120 秒单次与整体超时分别分类，恢复不超过总上限。
6. **安全提交**：取消、断电、保存失败、压缩中新增补充和编辑、候选覆盖不一致均不丢原文，不执行历史指令，不重放工具。
7. **旧数据**：旧文本/270 段/分层断点不被强删；来源不匹配不冒充可续压；新算法回滚仍可读取旧活动窗口。
8. **性能**：本地打包维持线性，完整日志区分保存/IPC/上传/模型等待；不把网络波动当作算法收益。

真实请求沿用明确授权范围；每批记录初始请求和安全重试数量。使用冻结数据做离线结构回归不等于允许将该数据自动发给任何服务商。

## 十一、迁移与回滚规则

- 只新增策略版本和可回滚适配层，不先批量改写已有 Journal/摘要。保存旧活动窗口及相关元数据后，再原子发布新版本。
- 在不改显式覆盖的前提下，对 null 的自动模式迁移做一次说明；不静默把 1 MiB 改成 2 MiB，亦不静默把显式软预算当成硬上限。
- 不同时调整全局重试次数、单次超时、整体预算或自动换供应商。质量/成本/延迟各自独立比较。
- 回滚退回已提交的活动上下文与旧读写器，不能按全 Journal 重建后直接塞回模型导致超窗。新状态不能被旧读写器理解时，应先建立兼容快照再启用。
- 每阶段先完成可评审源码、针对性回归及报告，再按既有要求申请具体 APK 安装与真实模型验收，不创建自动定时任务。

## 最终建议

**采用 Codex 可验证的 token 管理和新窗口承接思路，使用 Eta 上游的简单语义摘要与安全提交，并保留本地对超长历史的工程保护。默认业务收敛为一套流程；格式、分段和原生接口都只是后端选择。**

解决长对话应依靠“活动输入有界且能持续恢复空间”，而非更大的固定 MB 阈值、更多重试、更长超时，或更复杂的事实 JSON。
