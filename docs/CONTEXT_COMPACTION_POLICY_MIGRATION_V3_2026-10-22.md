# 压缩策略 v3：唯一配置语义、联合迁移与发布门槛

> 历史设计，已被 [v4 增长余量定稿](CONTEXT_COMPACTION_V4_IMPLEMENTATION_2026-10-22.md) 覆盖。本文把精确观测值直接作为 L 的规则禁止用于实现；新增候选采用显式启用、冻结 anchor/G/L、独立 B/H。实际实现和未接入项目以 v4 交付报告为准，以下保留供审计，不能视为当前默认或完成证明。

日期：2026-10-22。状态：设计，未实施、未安装、未发送测试请求。本文取代 v1/v2 冲突的配置、默认值、哈希和预算发布条款；引擎接口以 [独立设计](TEXT_COMPACTION_ENGINE_INTERFACE_2026-10-22.md) 为准。v2 的 usage 降级、质量/成本标准和故障分类在无冲突处继续适用。

## 1. B/L/H 唯一映射

当前实际只有 `model_providers.request_byte_budget`；新增配置尚不存在。迁移后此字段原值不变，**只表示 B**。L/H 在新的路由策略表，不复用此字段，也不根据 B 自动提高 L。

| 旧 request_byte_budget | 新 B | 新 L |
|---|---|---|
| NULL | NULL：无额外软字节触发，token/L/H 仍生效 | 独立路由策略解析值 |
| 正数 X | X：严格 bytes>X 时软触发 | 独立路由策略解析值，不自动等于 X 或 max(X,L) |
| 0 | 0：关闭软字节触发，token/L/H 仍生效 | 独立路由策略解析值 |

负数旧脏值不擅自解释为正数，标记待处理并沿旧 fallback 读取；写入新设置只允许 NULL/0/正整数。

- B 是用户选择的软摘要线，失败时是否可发原请求由后续发送检查决定。
- L 是本地自动发送边界，不证明 API 能力。未知 API 也有有限 L。
- H 是有证据且作用范围匹配的远端硬限制，未知为 NULL。
- **允许 B>L**，保留旧值而不偷偷抬高 L。此时界面明确“发送护栏会先于软阈值生效”；迁移预览及新设置保存时都提示，不承诺请求能增长到 B。用户可显式修改 L，但不能靠修改 B 间接提高 L。

### 1.1 唯一判定顺序

```text
测量当前模型最终协议 JSON 的 UTF-8 字节数 S，以及 token 压力
soft = B>0 && S>B
guard = S>L
hard = H 已知 && S>H

若 token/soft/guard/hard 任一成立：
  非 token 且仅 soft 的已知失败抑制可以延期本次软优化
  其他情况按容量与失败状态处理；能尝试时最多启动一次压缩任务
  无法安全重试且容量阻止发送时，保留状态并明确暂停

发送前，对最终实际载荷重新检查 token、协议、权限、L、H
仍越 L：需要严格绑定单次请求的许可；仍越 H：禁止发送
在 L/H 内但仍越 B：不再开第二个压缩循环，说明软目标未达/保留原请求
```

因此 **B<S<=L 且无其他压力时仍先触发软摘要**；只有 B 未触发或本轮软优化已按规则结束/延期时，才“正常发送”。L=X 时也不会让 B 失效：S>X 同时触发软线和护栏；两者只运行一个压缩任务。

既有 P0 白名单、取消、存储/未知错误、token/both 和签名保护不扩大。P0 允许发送原请求并不意味着可绕过 L/H。

## 2. 路由默认 L：不未经验收上调到 2 MiB

### 2.1 已有数字与单位纠正

封存 208 样本最大为 1,589,538 B（约 1.516 MiB）；额外冻结日志请求为 **1,782,914 B（约 1.783 MB / 1.700 MiB）**。“1.78 MiB”是此前单位混用，不是精确观测上界。存在其他较大的记录时须逐条核对，不能口头取整后当默认。

本设计对已核对的这一路由采用：**L=1,782,914 B，不向上取整**。来源标为 observed_success_boundary，不能称 validated_api_max。一次成功也不能证明所有更小请求都成功，大小不是唯一变量。

- 只有模型、协议、Provider、账号作用域、端点和相应网络条件匹配的证据才可用作此路由的来源。数据过期、配置改变或不能重现其作用域时回到可见的保守本地策略并提示，不能自动沿用大边界。
- **2 MiB 仅为专门验收后的候选边界**：至少两类有代表性的合法载荷在该体积附近各 5 次完整上传并收到有效响应，分网络说明，所有请求需事先授权。通过也只证明观测条件，不证明硬容量。
- 2.5–3 MiB 未经授权不自动上传。真实探测不作为日常聊天的隐藏副作用。
- 有明确用户配置的 L 优先（受 H 限制），其来源为 user_selected，不能冒充已验证。

### 2.2 无匹配证据的路由

- 已有路由：先以升级前解析出的本地默认预算作为迁移候选 L，来源 legacy_local_policy；显式 B 仍只映射 B。不能把一条 Provider 的证据推广到其他 API 或模型。
- 全新路由：首轮候选 L=512 KiB，来源 bootstrap_policy，可见可改，不声称这个体积已由 API 验证。它限制未知上传而不是识别窗口容量。
- 以上新默认只有在新摘要引擎与联合验收通过、用户确认一次迁移预览后启用。此前保持旧策略运行，不偷偷拆字段。保守 L 导致的暂停率必须进入发布门槛。

### 2.3 一次性越 L 许可

存入 `oversize_send_permits`，不是写回 Provider 设置：permit_id、conversation_id、operation_id、run_id、round、route_key、payload_digest、max_bytes、created_at、expires_at、consumed_at、process_instance_id。

- 仅当有明确用户点击时创建；绑定**同一份完整请求**的私有摘要和确切最大字节数，最多五分钟，运行结束立即作废。
- 发起 HTTP 前在事务中消费；没有开始上传也不返还已消费许可。崩溃后不恢复成未消费。
- 只覆盖一个 HTTP 尝试。安全重试若仍越 L，不自动复用许可；下一模型轮、下一工具结果、补充消息导致载荷变化、换路由一律不继承。
- 仍受 token/H/权限/签名/取消约束。许可不抬高 L、不关闭 B，也不能绕过真实接口硬限制。
- 对话结束/删除、到期、进程重启或请求摘要变化即失效；不存请求正文。普通发送不增加确认弹窗，只有越界被阻止时显示可选择动作。

## 3. 45 秒不先成为默认：先验证成功率

撤回“先把自动总预算改成 45 秒再观察”的上线顺序。新文本引擎先在相同已冻结场景下比较 45/60/90 秒候选；每个候选的全部片段与共享一次恢复都计入预算，保留既有单次 120 秒天花板。

选择**满足功能和质量门槛的最短预算**。45 秒不通过则不启用；如果三个候选都不通过，先修引擎/覆盖选择，不仅继续加超时，也不以更高暂停率冒充提速。

### 3.1 明确分母与终态

对每个 route、输入窗口组及负载类型记录 operation_id：

- A：被自动策略接收的独立压缩任务数量，一次任务内片段/恢复不新增分母。
- S：预算内摘要已原子提交、满足容量并可继续原请求的任务数；“生成了一段摘要”不是成功。
- P：预算耗尽/不能形成可发送候选而暂停的任务数。
- F：摘要失败数（包括摘要失败但回退聊天成功）；C：用户明确取消数。终态互斥，A=S+P+F+C。
- M：A 中后来需要用户手动重试/续压才完成的原任务数量，按 operation_id 去重；重启后保留关联。

既报 S/A、P/A、M/A 与取消率，也报排除故障注入和明确用户取消的受控成功工作负载分组；不能把慢任务从分母排除。自动允许发送原请求的 byte-only 回退计为 fallback，不计“摘要成功”，另报实际聊天完成率。

### 3.2 候选发布门槛

| 指标 | 门槛 |
|---|---|
| 自动完成率（非故障注入的受控负载） | >=95% |
| 预算暂停率 | <=5% |
| 需要手动介入的原任务占比 M/A | <=5%，不能靠用户救场满足自动成功率 |
| 摘要已提交后的原请求继续完成率 | >=95%，传输失败单列，不能删掉失败样本 |
| 暂停/失败后保留 | 原请求、草稿、附件引用、Journal、已验证断点 100% 保留；重启后可继续，工具重放为 0 |
| 质量、成本、缓存 | 沿 v2 独立门槛，缺失观测不写通过；不能靠压缩遗漏内容提升成功率 |

先每路由 20 个有效自动任务作试点，覆盖至少 4 个不同会话和两种负载；正式默认迁移前每路由至少 100 个任务，跨至少 10 个会话/3 天，并覆盖代表性的 128k/1M 输入预算组。报告计数与置信区间，不把高度相关轮次等同独立场景；点估计达标不代表总体成功率已经被统计证明。

必须包含正常可成功文本摘要、完整 20,300 字符输出、正常多片累计摘要和需要恢复的案例，不能只测试把 80.8 秒失败截成 45 秒暂停。真实请求的范围和批次上限另行批准，优先复用冻结数据；这不是本次授权。

artifact 正文在应用私有文件中按不可变内容寻址保存，权限与既有摘要目录一致，不进入失败表/遥测。manifest/node 必需字段和存取接口见独立引擎文档。

SQLite 迁移只建表、索引和默认列，不在迁移事务中遍历全部会话生成哈希、转换 270 段断点或复制所有正文。路由 profile、摘要适配和哈希索引按需分批建立；策略未 review/ready 时不能按新默认发请求。

实现需给出同版本 Room Entity/DAO、迁移测试和 rollback APK，不只是可解析 SQL。当前 destructive fallback 不可用于这条升级或不支持的降级：遇到缺失迁移应停止并保留数据库。

### 4.2 UI 一起交付

- 原“请求大小软预算”保留，仍编辑 B，清空/0/正数说明明确。
- 新增高级项“自动发送大小边界”：显示继承路由值或用户 L，精确字节数和来源；B>L 显示护栏先触发。
- “接口已知上限 H”只读展示证据和范围，无证据显示未知；手动填 L 不会让 H 变成已验证。
- 一次迁移预览逐 Provider/路由列旧值→B/L/H，说明 0 不关闭 L/H；不接受迁移时可继续旧引擎/旧策略，不强制全库切换。
- 失败通知提供“重试压缩/继续压缩”；越 L 阻止发送时才提供严格一次性许可入口。两种入口含义不同，手动重试不等于批准大请求。

## 5. 来源哈希的性能约束

撤回“每次对完整巨大前缀重新做一次 HMAC”的可执行解释。新 canonical_version=2：**流式叶摘要 + 持久化有序范围树 + 对范围根做 HMAC**；它与 v2 草稿的全文 HMAC 不兼容，因此旧失败记录失效，旧已验证摘要不会被删除。

- 叶摘要对固定字段顺序、带长度分隔的持久化消息内容计算；正文/content_json/工具 JSON 按存储字符串原始字节流处理，不为哈希解析整份任意 JSON。等价但不同序列化允许保守失效，不能漏掉真实编辑。
- 写入新消息时流式计算并保存叶摘要；正文变化使叶和相关祖先失效。顺序、ID、role、工具配对及摘要标记均纳入。
- O(log N) 指尾部追加和位置不变的单消息内容更新。中间插入、删除或重排可使后缀索引失效，须分批重建，不声称也是 O(log N)，也不在发送主线程同步完成。
- 有序 Merkle 节点带域分隔、消息数和字节长度，范围查询 O(log N)，不从 5,000 条消息重新编码大列表。source_digest=HMAC(key,canonical_version+ordered_range_root+范围身份+语义版本)。范围根不直接当作全文序列化哈希冒用。
- 大消息增量读取最多 64 KiB/块，hash scratch heap 上限候选 2 MiB；不得把全文 toString()/toByteArray() 后再算。只用一个后台工作者，每最多 16ms 或 64 KiB 让出执行，禁止主线程算哈希。
- 冷索引不在 Room 迁移中构建；按需/空闲分批，检查取消和总 deadline。首轮确需校验的耗时也计入端到端指标并显示本地校验进度，不排除它美化延迟。
- 重启后复用持久索引前检查内容版本/树 generation；不信任只有相同条数的旧索引。旧消息 ID 若缺失或不稳定，先采用保守流式验证，不伪造稳定身份。

### 5.1 性能门槛与夹具

在明确记录配置的 RMX3888 上，分别测试 5,000/10,000 条、16 MiB/128 MiB 总原文，另加单条 16 MiB 工具结果；不调用模型。

| 场景 | 候选门槛 |
|---|---|
| 索引就绪后的前缀/区间摘要，连续 100 次 | P95<=20ms，hash scratch 增量<=2 MiB |
| 尾部追加/中间单消息编辑 | 仅修改叶及祖先；不得重新编码全前缀；除该消息字节读取外 O(log N)，索引操作 P95<=50ms |
| 首次冷索引，5,000 条/16 MiB | 墙钟 P95<=3s，CPU<=2s |
| 首次冷索引，5,000 条/128 MiB | 墙钟 P95<=15s，CPU<=10s；scratch<=2 MiB，不产生整份复制 |
| 取消/库迁移/主线程 | 最迟一块读取或一次让出后响应取消；DB 升级不做全文扫描；主线程哈希时间为 0 |

100 次热查询只用于性能分布，不作为 100 个独立质量场景。冷热各至少 5 次重新建索引测原始数据；未达标则先优化或明确首次处理成本，不把索引工作藏到“模型思考中”。以上未执行。

## 6. 发布与回滚前置条件

1. 先完成文本引擎接口与真实成功路径，再评估自动 deadline；不能先改预算掩盖失败。
2. 迁移、B/L/H UI、一次许可、失败记录、哈希索引一致交付，策略未 ready 继续旧路径。
3. 本地测试与经批准真实试点均通过才默认切换；新 L 的上调独立验收，不随代码更新悄悄进行。
4. 数据库已经升级到 v25 后，**不能直接装原 v24 的 2002 包回滚**，现有 destructive fallback 有清库风险。回滚包须保留 v25 schema/迁移与兼容读取，仅切回旧引擎；配置回滚优先。
5. 恢复升级前数据库备份会丢升级后的新增内容，不能称无损回滚。需要额外方案和明确授权，不自动执行。

本文仅设计；数字是准入门槛，非已验证 API 容量或已达成性能。
