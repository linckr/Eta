# 3.3.3 数据、认证与模型设置迁移说明

## 实现范围

- 数据库联合版本为26，支持官方22/23与本地23/24/25直接收敛。迁移按实际表列补齐auth_mode、模型窗口含义/输入限制、B、发送策略和失败表；不启用destructive fallback，不重写历史、Journal或检查点正文。
- 保留本地模型容量解析和手动覆盖。自动窗口展示在输入框但未编辑保存时不固化为override；刷新远端值可更新自动值，已编辑文本保留。总窗口与输入上限分开；无效别名不能阻断其他有效别名。
- 新远端目录使用上游账号binding/session generation核验，API-key目录不能假装OAuth账号目录。保留本地删除Codex远端模型后的隐藏名单和显式重置恢复行为。
- 本地请求软预算与v4发送边界设置完整接入新Provider配置页；新OAuth不能绕过本地预算、窗口和独立压缩模型配置。
- Provider创建时间总是序列化，修复默认时间表达式在跨毫秒解码时丢失原创建时间的问题，不改变B的默认语义。

## Codex凭据承接与单一所有者

主进程初始化新凭据仓库时，尝试读取本机旧Keystore加密文件，映射成新按Provider存储。目标为旧内置Codex连接，以及原有严格官方Codex base URL的订阅连接；已有新格式凭据优先，绝不覆盖。

每份新凭据原子写入后读回核验；全部完成才写退休标记。旧密文保留作恢复副本，但正常请求工厂不再选用旧刷新路径，退休标记防止登出后从旧文件复活。导入失败不删除旧文件、不阻止其他功能启动；旧文件无法解密或缺工作区信息时需要重新登录，真实导入/刷新仍需另行验收。

新配置页同时保留上游浏览器登录和“使用设备码登录”。设备码入口复用旧协议请求，但以persist=false返回结果，保存和刷新统一由新ProviderCredentialSessions负责；取消检查在轮询及最终保存前执行。不存在两套同时写回同一运行账号的刷新owner。

账号登录、登出或forget会清除该Provider已冻结发送策略；失败表的HMAC键不含可索引Provider列，因此保守清空全部内容无关失败元数据，保留原历史和检查点。完成事务后通知Room失效跟踪，Provider Flow可重新加载。普通token refresh不使策略失效。scope另外加入authMode与providerId，避免不同连接复用旧证据；已有旧scope策略需要重新明确启用。

## 本轮验证与边界

新增官方22、官方23、本地23/24/25五类SQLite旧库夹具，并通过Room最终schema验证检查模型、历史、预算、策略和失败记录保留；另有旧凭据纯映射、账号变动与普通刷新失效区别测试。

实际测试运行结果由统筹交付报告记录。本说明不把新增测试源码、编译通过或安装启动等同于真实OAuth登录、订阅刷新、远端模型拉取或模型会话成功。本次代理未安装APK、未发网络/真实模型诊断请求、未读取真实凭据内容到电脑。
