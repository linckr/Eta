## 一、结论摘要

本轮取得 **208 个去重后的 chat 请求前检查及 208 个对应 HTTP 完成记录**，全部 HTTP 200、完整上传，无已记录上传失败或非成功 HTTP 状态。请求体为 **898,785–1,589,538 B（0.857–1.516 MiB）**，P50 为 1.277 MiB。

- 512 KiB：208 / 208 超过阈值；1 MiB：177 / 208（85.10%）超过阈值。
- 所有已记录预算检查的运行时 reason=none，有效输入预算均为 1,000,000 tokens；估算输入占比为 29.36%–50.46%，低于现有 85% token 触发线。
- 客户端请求体写入阶段 P50 **164 ms**、最大 277 ms；HTTP 请求整体 P50 **3,513 ms**、最大 19,500 ms。本批未显示约 1.5 MiB 以内请求体写入构成主要等待。
- 对本轮实际工作负载，1 MiB 仍会使大量已成功请求落在纯字节压力区间。它足以修正早先 540,885 B 基准，却不足以代表这批更长历史的合理默认。
- **这不是供应商硬上限测试，也不能证明默认 48 MiB 合适。** 本批最大实际请求仅 1.516 MiB。

本报告建议保留当前策略 PR 的待评估状态，把 **DeepSeek 单独的 2 MiB 软预算**作为下一轮候选，并把压缩后的字节余量与阈值变更分开评审；不据此提高所有 Provider 的默认值。本次仅出具报告，未实施该候选。

单位 MiB=1,048,576 B。分位点采用既有分布工具口径：排序后取 `round((N-1)×q)` 的零基位置；偶数样本的 P50 为该离散分位点，不是两个中间值的平均。

| 指标 | 请求体（B） | MiB |
| --- | ---: | ---: |
| 最小值 | 898,785 | 0.857 |
| P50 | 1,338,989 | 1.277 |

| 最大值 | 1,589,538 | 1.516 |
| 平均值 | 1,306,278 | 1.246 |

208 个记录按采集顺序比较，207 次相邻比较中有 **197 次体积不下降**。这与连续长任务/历史增长相符，说明样本高度相关；不能据此确认只有一个会话，也不能把 208 次请求当作 208 个独立用户或独立场景。

这些计数沿用严格 `request_bytes > threshold`，等于阈值不算超过。由于记录中的 token 压力均未触发，它们可用于本轮“纯字节压力”的 shadow 对照。

**不能把 177 / 208 表述为“启用 1 MiB 后实际会压缩 177 次”。** 一旦首次真实压缩改变上下文，后面的请求体就会变化；这里没有模拟压缩质量、成功率及后续上下文演化，也没有完整模拟自动压缩关闭、签名工具轮次延后等分支。

因此，512 KiB→1 MiB 在这批原始请求上仅使 31 个记录不再越线；这个 14.90% 是静态越线计数差，不是已测得的实际耗时下降或压缩次数减少率。

## 五、耗时与上传结果

| 指标 | 客户端请求体写入阶段（ms） | 单次 HTTP 总耗时（ms） |
| --- | ---: | ---: |
| 最小值 | 101 | 1145 |
| P50 | 164 | 3513 |
| P95 | 205 | 9953 |
| P99 | 245 | 14288 |
| 最大值 | 277 | 19500 |
| 平均值 | 159.606 | 4310.712 |

计时定义与限制：

1. 写入阶段 = write_completed.elapsed_ms − write_started.elapsed_ms。它是客户端 HTTP 生命周期的观测，不是服务端确认收齐请求体的独立计时，也不包含此前连接建立时间。
2. HTTP 总耗时 = http_call_completed.elapsed_ms，包含连接、写入、等待响应及响应读取，不是整个 Agent 任务耗时。
3. 写完至收到响应头 P50 为 254 ms、P95 为 550 ms、最大 997 ms；响应头至 HTTP 完成 P50 为 3,001 ms、P95 为 9,595 ms。
4. 分阶段分位数来自各自排序，**不能把各段 P50 相加当作总耗时 P50**；响应读取阶段包含网络、网关缓冲和模型输出，不能直接称为纯模型计算时间。

全部 208 个完成记录为 HTTP 200，0 个明确上传失败，0 个非成功 HTTP 状态。HTTP 200 不单独证明回答内容正确、协议正文完整或业务任务已解决；本轮未保存回复正文，不做语义质量验收。没有原始请求体，也无法审计网关内部是否发生隐藏重试。

本轮没有记录可验证的网络路线，不能把结果泛化到蜂窝网络、其他 Wi-Fi、Tailscale、WorkBuddy 或 intern-ai。

## 六、证据边界

### 可以确认

- 本次设备、配置和实际链路接受了 208 个 0.857–1.516 MiB 的已捕获请求，均记录为完整上传及 HTTP 200。
- 对这些观察到的请求，512 KiB 和 1 MiB 字节阈值会产生大量与 token 压力无关的越线判断。
- 本批客户端上传写入阶段较短，没有复现过去约 120 秒的写入中断。
- 采样结束后临时覆盖已恢复留空，未修改本地压缩策略实现、未额外编译或安装。

### 不能确认

- 供应商 HTTP 请求体硬上限、48 MiB 是否可靠、2 MiB 以上的实际行为。
- 其他模型窗口、其他提供商或其他网络的合理默认值。
- 真实部署 1 MiB / 2 MiB 后的实际压缩频率、摘要信息质量、缓存命中变化或任务成功率。
- 208 个独立场景或长期跨日可靠性；零失败不等于未来零失败。
- 每个请求创建时的精确模型快照、全部并发任务归属及设备全量覆盖。

供应商归属条件为“单一活动 UI 会话绑定 DeepSeek + 48 MiB preflight”，后续按 PID/TID、体积和 trace_id 关联。另一 Provider 同时也可能配置相同预算，所以没有仅凭 48 MiB 数值判断归属。并发、无可确认 UI 绑定等请求会被排除；任务中途变更会话绑定模型仍可能影响归属。下一版埋点应增加请求创建时的安全 Provider/run 关联，不记录凭据或正文。

## 七、建议的后续工作

1. **保留当前 P1 PR 的待评估状态。** 精确 540,885 B 基准已被修正，但不能据此直接合并为适用于所有大窗口模型的最终策略。
2. **优先评估 DeepSeek 单 Provider 的 2 MiB 候选。** 它覆盖全部已观察请求，最大样本约为该阈值的 75.80%；这只是有余量的下一候选，不是对 2 MiB 服务端能力的实测结论。2 MiB 与 4 MiB 在本数据上都为 0 次越线，本轮无法证明哪一个在未来更优。
3. **独立设计压缩后的字节余量。** 当前仅要求压后不超过阈值，仍可能因新增工具结果很快再越线。需结合受保护的最近消息/工具边界与最终序列化预算，评估更充分的缩减目标；不能强删原始结果来满足阈值。
4. **保留所有现有保护。** token 压力、Provider 超窗恢复、手动压缩、P0 byte-only 失败回退、取消及断点边界保持原规则；不凭本批数据扩大模型请求重试次数。
5. **先离线回归，再决定是否进行新增真实验收。** 覆盖 2 MiB 边界、显式配置优先、换模型、未知窗口、P0 回退/取消/检查点与工具不重放。大于本批最大值的真实请求需另行授权，不能为测上限自动发送真实历史。

以上均为报告建议。本次没有调整 PR 策略、创建新模型请求、再次编译或安装，也没有把预算留在 48 MiB。
