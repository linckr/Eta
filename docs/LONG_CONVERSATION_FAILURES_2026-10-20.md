# 长会话反复压缩与首响应延迟调查

## 范围与当前状态

对象为手机上的“P1 1901 预算验收（冻结样本）”，DeepSeek / deepseek-flash，Responses API。本文不包含会话正文、密钥、工具参数或结果。两项问题依次处理。

- 2026102001 已经用户授权安装：反复失败后的单轮保护、事实条数针对性纠正已实现；69 项回归通过。
- 请求前等待已在 2001 真机定位至跨进程请求打包；2026102002 已修复旧兼容预览的二次方序列化，完成编译、签名和授权安装，同一长会话打包实测由 43,475 ms 降到 357 ms。
- 当前无全局预算策略变更，也没有合并待评估的 1 MiB 策略 PR。

## 1. 为什么每次工具调用后都再次压缩

当前大窗口模型留空预算按 1 MiB 派生。此前 2 MiB 临时验收结束恢复留空后，约 1.7 MiB 的请求重新越过软预算；这是本次触发频率升高的配置因素。

运行循环每轮模型请求前检查最终协议 JSON 字节数。摘要结构失败后，P0 回退允许字节压力下继续发送完整原请求；历史不改变，下一条工具结果加入后再次越线。原实现没有在同一轮用户任务内抑制已失败的字节优化，因此每次工具后都可能重新付出摘要成本。

原会话冻结前缀之后有 31 条压缩记录，记录中的累计 elapsed 为 1,135,644 ms（约 18 分 56 秒）。这包括取消、手动尝试，不能说是 31 次独立自动失败。结构错误诊断中 leaf/fact_count 27 条、leaf/fields 1 条、leaf/json 1 条；错误与重试记录也不能等同于独立任务数。

### 摘要事实条数的直接证据

获得用户授权后，使用同一供应商、原历史的一个有界片段以及当前叶摘要指令进行诊断：

| 项目 | 原指令 | 加入针对性纠正的一次重试 |
|---|---:|---:|
| HTTP | 200 | 200 |
| 完整响应 | 是 | 是 |
| facts 条数 | 17 | 16 |
| text 总字符 | 2022 | 2681 |
| 总耗时 | 5.016 s | 6.643 s |
| 来源一致、JSON 有效 | 是 | 是 |

客户端接受 1–16 条，故 17 条即失败。旧重试只给泛化格式要求，对 fact_count 不会生成具体纠正。该诊断是原历史代表片段，**不是过去某次失败请求的精确重放**；不能据此断言 27 条历史错误全部返回 17 条。原记录没有保存实际计数，候选新增只记录数字的安全诊断。

### 修复边界

1. 字节压力的已知摘要失败或无收益后，同一用户轮次内后续工具轮跳过自动字节摘要，发送原请求。延期动作单独记为 deferred，不算新压缩尝试。
2. 新用户补充、新运行或成功压缩后允许重新尝试。没有跨运行永久关闭，也没有放宽模型 token 容量门槛。
3. token/both 压力、手动压缩、供应商超窗恢复仍走原保护；取消、存储失败、未知故障不被软化。
4. facts 超限/为空的一次结构恢复明确返回条数、1–16 条及正文容量要求，让模型重新归纳；不截断数组，不接受非法摘要，不推进未验证断点。
5. Journal、工具结果、来源和原子提交规则不变。该修复不等同于尚待实施的“压缩后字节余量”设计。

## 2. 为什么长会话发送后很久才有内容

临时只关闭 DeepSeek 的字节软预算触发，保留 token 容量保护，以排除压缩等待。结束后已恢复原值 NULL。

同一提示要求一句话总结、不调用工具，原会话和有效隔离会话均没有工具调用、没有摘要请求：

| 边界 | 原长会话 | 隔离新会话 |
|---|---:|---:|
| 点击发送至观察到运行结束（约） | 67.509 s | 3.679 s |
| 请求前本地等待（约） | 45 s | 1.3 s |
| 请求体 | 1,781,578 B | 94,549 B |
| 成功上传所在 HTTP 调用：写完请求 | 9.529 s | 0.340 s |
| 同一 HTTP 调用：首次正文 | 12.266 s | 1.920 s |
| 最终状态 | 200，完整结束 | 200，完整结束 |

长会话还出现了一次连接/上传阶段中断并安全恢复，故不能将两个请求的总差值全归为固定的本地代码成本。两次短回答均未产生 reasoning delta，上表首次正文不等同于首条思考。该对照仅一次有效配对，非稳定延迟分布。

历史实际输入约 49–50 万 tokens，缓存输入占绝大多数，不能直接解释为所有旧历史都重新做无缓存预填充。

当前可确认的延迟组成：失败压缩会额外增加等待；即使排除压缩，长会话还有明显请求前等待和较慢大体积上传。

### 2001 真机分段定位

同样提示、关闭字节摘要干扰的授权请求：

| 阶段 | 耗时 |
|---|---:|
| UI 保存提交 | 305 ms |
| UI 配置准备累计 | 435 ms |
| Runtime 绑定 | 0 ms |
| Client 打包至 payload_ready | **43,475 ms** |
| Runtime 初始化至 model_ready | 71 ms |
| 模型请求 HTTP 完整结束 | 12,958 ms |
| 点击至运行退出 | 59.009 s |

热点在 `AgentRuntimeWire.requestBundle` 内用于旧版本兼容的 `AgentLegacyConversationProjection.encode`：每删除一条旧消息就重新 JSON 序列化整个剩余列表，实际是二次方的累计工作。完整历史已经走独立 FD 传输，兼容预览却仍阻塞新请求发出。

2002 改为每条消息仅序列化一次、计算精确 UTF-16 后缀长度，再按旧规则选择预览起点。保持原输出边界、孤立工具结果处理、单消息降级和脱敏语义；完整 FD 历史与持久化历史不截断。

2002 Trace `d99438f9-bf1c-44e8-904c-ba24f2974e08`，HTTP 200、完整完成、无思考 delta、无工具调用、无自动摘要。请求随诊断消息略增，并非通过削减实际历史提速。单次总时间也受网络波动影响，核心可归因的本地改进是打包阶段从 43.5 秒到 0.36 秒；剩余等待大部分在 HTTP 上传及上游响应，不承诺长会话等同新会话速度。

结束后核对无在途任务，DeepSeek 字节预算恢复为原值 NULL。2026102002 为当前安装包。防重复摘要的多工具轮行为由本地回归覆盖，本轮真机授权只做总结，不声称已进行新的真实多工具长任务验收。

回归对照 38 组历史、每组 7 个容量（共 266 个组合），包括 Unicode、转义、图片脱敏、连续工具结果、空列表与超长单条，结果与旧算法逐字相同。1,800 条合成历史的新预览生成在本机 JVM 为 13 ms，不能把这个数字当作手机耗时。

### 分段计时候选

新增 `agent_request_preparation`，以 run_id 关联，只包含固定阶段名、组件及单调时钟耗时：

- UI：queued → persisted → config_ready。
- Client：queued → bound → payload_ready → sent。
- Runtime：queued → checkpoint_ready → skills_ready → context_ready → model_ready。
- 后续接已有预算与 HTTP Trace。

不绕过用户消息预写事务，不保存会话正文或凭据。2001 定位结果如上，2002 保留计时用于修复后的实测。
